# Web Admin Phase 3 — Reference Data, Runtime Comparison & DB-Backed Calibration

**Дата:** 2026-08-20
**Статус:** дизайн на затвердження користувачем (грумінг-сесія)
**Гілка:** `v1-1-stage`
**Передумова:** validation study (spec 2026-08-20-profilometer-validation + A1) —
його `match.py`/`calibrate.py` стають бібліотекою цієї фази.

## 0. Вердикт здійсненності

Реалізовно повністю, без нових важких залежностей: парсер форм і вся
математика порівняння/калібрування вже написані й протестовані у
`studies/profilometer_validation/` (21 тест); адмінка вже має чергу, артефакти
і сховище метаданих. Нова робота — 3 сутності БД, ~6 ендпоінтів, воркфлоу
підтвердження і фронтенд-вкладка з інтерактивними графіками. Один принциповий
нюанс: **книжкові константи лишаються в коді** (правило integrity);
БД зберігає лише додаткові іменовані набори, які пайплайн отримує через уже
наявні параметри `iri_psd_A/B` (і аналогічно bias-корекцію Eq.6 — постобробкою
без зміни фізики пайплайна).

## 1. Модель даних (нові сутності)

**ReferenceDataset** — завантажена форма профілометра:
`id, filename, uploaded_at, road_name, direction, lane, category, step_m,
measured_at (ручне поле — клітинка дати у формі буває застаріла!),
intervals_count, chainage_span_m, bbox, parse_warnings JSON, source_deleted`.
Розпарсені інтервали зберігаються на диску
(`storage/reference/<id>/intervals_10m.parquet|csv` + оригінальний xlsx);
у БД — лише метадані. Канали 1–8; дублікати 9–10 відкидаються з попередженням.
При завантаженні — та сама валідація структури, що в дослідженні (жорсткий
пошук хедера, суцільність пікетажу).

**Comparison** — зіставлення «ран × еталон»:
`id, run_id FK, reference_id FK, created_at, status
(queued|running|done|failed), params JSON (tolerance, min_rows —
дефолти зі студії), result_dir, summary JSON, error`.
`result_dir` містить: `matched_pairs.csv`, `stats.json` (той самий формат, що
у study — per-road чесність вбудована), серверні PNG/PDF-фігури
(matplotlib, той самий figures-код) і `chart_data.json` — компактні серії для
інтерактивних фронтенд-графіків.

**CoefficientSet** — іменований набір коефіцієнтів:
`id, name (унікальне, напр. UA_2026_van_SM-S948B_eq6bias), model
('eq3'|'eq6_bias'), params JSON ({A,B} або {bias}), vehicle_type,
phone_model, status ('draft'|'confirmed'|'archived'),
comparison_id FK (провенанс!), stats_snapshot JSON (R²/MAE/LORO на момент
фіту), created_at, confirmed_at, confirmed_note`.
**Інваріант:** не більше одного `confirmed` набору на ключ
(model, vehicle_type, phone_model) — підтвердження нового архівує попередній
(історія зберігається, нічого не видаляється).

**AnalysisRun** (розширення): `coefficient_set_id FK nullable` — яким набором
рахувався ран; `null` = книжкові константи. Пишеться і в `report.md` рану
(вже підтримано прапорцями).

## 2. Резолюція коефіцієнтів для нового рану

При створенні рану бекенд читає `vehicle_type` і `device` з
`recording_meta` файлу та шукає confirmed-набір:
1) точний збіг (model, vehicle_type, phone_model) →
2) (model, vehicle_type, phone_model=NULL) →
3) книжкові константи (Eq.3 book + Eq.6 без корекції).
Обраний набір фіксується в рані (снепшот id + params у summary) — ран
відтворюваний навіть після архівації набору. UI показує чіп набору на рані.

## 3. Порівняння в рантаймі

`POST /api/comparisons {run_id, reference_id, params?}` → job у ту саму чергу:
1. Перевірка сумісності: bbox рану перетинає bbox еталона (інакше fail з
   поясненням); ран `done`; направлення руху звіряється як у study.
2. `match.windowed_reference` (10 м еталон, ті самі дефолти) → пари.
3. `calibrate.*`: валідаційні статистики per-road… тут «road» одна — отже
   per-comparison; Bland–Altman; фіти eq3 і eq6-bias зі stats_snapshot;
   ефективний n; influence. Гейти зі study (R²>0.85, MAE<0.5) виводяться
   як індикатори, НЕ як автоматичне рішення — рішення за людиною.
4. Фігури: PNG/PDF (matplotlib) + `chart_data.json` (для інтерактиву:
   точки scatter (sqrtPSD, iri_ref, seg_id, chainage), серії профілю,
   різниці для BA).
5. З результату можна створити `CoefficientSet` (draft) однією кнопкою —
   з провенансом на comparison.

## 4. Воркфлоу підтвердження (вимога користувача)

Стани набору: `draft` → (кнопка «Підтвердити», з полем нотатки) →
`confirmed` (+ архівація попереднього confirmed того ж ключа) → `archived`.
- Драфт нічого не змінює в системі.
- Підтвердження активує набір ЛИШЕ для майбутніх ранів і відкриває діалог:
  «Перерахувати N наявних ранів (vehicle_type=X)?» — реаналіз створює НОВІ
  рани з новим набором (старі лишаються недоторканими, історія «як було до»
  зберігається); після завершення — пропозиція перебудувати глобальну мапу.
- Ендпоінти: `POST /api/coefficient-sets/{id}/confirm`,
  `POST /api/coefficient-sets/{id}/archive`, `GET /api/coefficient-sets`.

## 5. Frontend

**Нова вкладка «Калібрування»:**
- список еталонів (upload xlsx з прев'ю: дорога, пікетаж, крок, к-ть
  інтервалів, попередження парсера; поле «дата вимірювання» — ручне);
- список порівнянь зі статусами; сторінка порівняння: KPI (ρ, r, MAE, bias,
  n, n_eff), **інтерактивні графіки** (див. нижче) + кнопки «PNG/PDF»
  (серверні фігури), таблиця пар з підсвіткою найгірших розбіжностей,
  формули моделей з підставленими коефіцієнтами (KaTeX не тягнемо — акуратний
  HTML/типографіка);
- список наборів коефіцієнтів: статуси, провенанс (лінк на порівняння),
  снепшот метрик, кнопки Confirm/Archive з підтвердженням.

**Інтерактивні графіки:** легка SVG-реалізація власними компонентами на
signals (scatter із зумом/ховером/кліком → сегмент; профіль уздовж пікетажу з
brush-виділенням; Bland–Altman) — БЕЗ важких chart-бібліотек (перф-вимога
користувача; наш дашборд уже має CSS-гістограму). Токени дизайн-системи.

**Run page (пункт 3 користувача):** секція «Всі артефакти» (список файлів
result_dir з розмірами і лінками), і якщо для рану існують порівняння —
блок «Порівняння з профілометром» зі зведенням і лінками.

## 6. Що НЕ робимо (межі)

- Не переносимо книжкові константи в БД — вони в коді, під тестом-піном.
- Не даємо авто-підтвердження за гейтами — рішення завжди ручне.
- Не редагуємо форми еталона в UI (тільки upload/перегляд/видалення).
- Повне Eq.6-рефіт калібрування (не bias-only) — після накопичення доріг.
- Порівняння двох ранів між собою (Фаза 2) — окремо, поза цією спекою.

## 7. Тестування

Backend: юніт на резолюцію коефіцієнтів (3 рівні фолбеку), на інваріант
одного confirmed, на воркфлоу станів, на parse-upload xlsx (фікстура-форма),
на comparison job зі стабом матчингу; інтеграційний smoke: upload форми +
ран → порівняння → draft → confirm → новий ран бере набір. Frontend: спека
на резолюцію відображення чіпа набору, на confirm-діалог, на рендер scatter
з фікстурними chart_data. Регресія: всі наявні сюїти зелені.

## 8. Порядок реалізації (високорівнево)

1. Бібліотекизація study-коду (спільний пакет для бекенда) + парсер xlsx
   як сервіс. 2. БД-сутності + резолюція коефіцієнтів у create_run.
3. Upload/перегляд еталонів. 4. Comparison job + stats + chart_data + фігури.
5. CoefficientSet + confirm-воркфлоу + реаналіз-діалог. 6. Frontend вкладка
«Калібрування» + інтерактивні графіки. 7. Run page доробки. 8. Докі, правила,
регресія.
